## 1 引言

1.1 标识

系统名称为城院帮，项目标识HZCU-CampusHub，文档标识G04-FAR-2026。本报告用于课程项目可行性分析与实施方案选择。文档版本V1.6，修订标识G04-FAR-20261101-01，修订日期2026年11月4日；项目计划排期基准G04-BL-20261028-01。

1.2 背景

准备实习与求职时，学生需要搜集资料和面试经验，判断分享是否适合自己的专业、基础和目标岗位，并整理可执行的准备路径。前期需求讨论提出资料分散、筛选耗时、相似起点经历难找，以及缺少进一步交流渠道等问题。公司与岗位的面试流程、准备重点也需要便于查找和比较。[6]

研究依据为前期需求讨论、校内求职场景分析及公开软件资料比较。分析聚焦资料检索、经历背景匹配、面试经验复用和作者交流四类需求；用户操作反馈纳入需求评审及试用任务。

开发方为G04两名成员，面向本校求职读者、经验作者和管理维护人员。小组承担课堂项目投入，正式交付环境为本机课堂演示；持续公网运营作为后续条件另行评估。

4.2 现状逻辑与进一步定义的问题

现状的物理渠道包括网页、群聊和文档；抽象成逻辑过程是“搜索多种来源、人工比较适用性、个人保存、再寻找交流对象”。新系统把岗位与经历背景作为共同检索信息，把可复用的经历和评论保留在同一内容对象下。再将这一逻辑模型落实为客户端、业务服务和存储。该过程对应由现有物理系统到现有逻辑、拟建逻辑再到物理解法的推导。[12，PDF第10—11页]

| 问题 | 成因与边界 | 改进想法 | 验证方式 |

| P01 同类资料多，适用性难判断 | 读者还要比较作者专业、当时基础与应聘岗位，原链接并不能自动回答是否适合自己。 | 少量经历背景＋岗位主入口＋同专业和公司筛选；背景信息可由作者完善。 | 试用时能说明文章与自身起点的相似处及差异。 |

| P02 准备过程缺少连贯记录 | 面试题片段不能直接说明先准备什么、做过哪些项目、怎样投递及失败后如何调整。 | 鼓励写准备、投递、面试、结果和反思的亲历；采用可跳过的正文提示。 | 作者能按自身经历自由写作，不被多步必填表单阻断。 |

| P03 有用交流难持续发挥作用 | 一次答复与后续读者的问题可能脱节，作者也缺少持续维护的反馈。 | 文章与评论绑定、收藏和非现金投币反馈；作者自愿留站外联系。 | 能从文章找到相关评论并反馈问题；站外协商不进入平台订单。 |

| P04 开放分享需要校内治理 | 校园认证只能说明审核状态，不能替代内容真实性判断。 | 先发布后管理、反馈举报、管理员定位与记录理由。 | 越权、广告和争议经验场景进入SRS、举报处置和测试。 |

上述问题分别对应检索筛选、经历背景、创作提示、评论交流及社区治理功能。试用检查读者查找适用经历、作者完成创作和管理员处理反馈的任务完成情况。

社区采用先发布后管理，管理员查看反馈举报并一键定位文章和评论，记录理由、处理结果和复核情况。普通学生账号与管理账号分开，作者不能以自己的权限删除他人真实评价或绕过处理记录。广告、欺骗性内容及公司避坑文章中的争议信息，要有报告入口和处置流程，不能靠“已校园认证”代替内容真实性判断。

管理员处理流程为登记对象、检查内容与证据、决定处置、记录理由、反馈和必要复核。找不到原对象、重复举报、误操作或意见争议也需要可追溯状态；上述细节在需求中形成可验收规则，管理网页以减少查找和跳转为目标。

部署与维护操作

独立运维网页需要直接执行部署、重启和恢复，同时提供状态、错误日志与备份记录。它通过固定动作执行器操作既定服务，避免把网页设计成任意命令终端。执行前检查角色、目标和版本，危险动作确认，运行中的部署恢复互斥，结果和错误持久保存。

恢复同时检查数据库、图片与版本清单。先保护当前状态，再验证备份摘要与兼容性，必要时停止写入，恢复后检查关键记录、图片和币账本；失败时按既定保护与回退流程处理。备份文件或密码不能写入公开仓库，维护说明记录操作方式而非实际账号密码。

交付时两人按说明完成本地冷启动和维护交接，保存构建包、环境、初始化数据、已知限制和恢复记录。云服务器不是正式演示依赖，公网域名、备案、小程序发布及持续服务保障也不由课堂演示结果自动满足。

9.2 使用人员和培训

读者和作者依据界面提示完成阅读、认证和创作；社区管理员接受举报处置、角色授权与隐私培训，运维人员完成部署和恢复演练。两名成员依据手册交叉操作，记录任务完成情况、帮助需求及异常处理结果。
