## 2 用户使用方式

当前后端为Java项目，本批用同一份代码和同一JAR的两种运行配置实现debug/release，不维护两套业务代码。模式切换重启生效，不做网页热切换。

| 模式 | 用户目标 | 实际行为 |
| --- | --- | --- |
| debug | 本机开发、联调和排障 | 开启本项目安全DEBUG事件及受控诊断文件，记录具体动作、阶段、错误码和可定位的本项目代码位置。正常运行日志、业务审计继续生效。 |
| release | 正常演示与运行 | 默认模式；关闭本批调试事件和诊断文件新增写入，保留INFO/WARN/ERROR必要运行记录、traceId及关键业务审计。 |

预期启动入口：

```powershell
./scripts/Start-Server.ps1 -Mode Debug
./scripts/Start-Server.ps1 -Mode Release
```

这两条是需要实现并真实验证的目标用法，目前旧脚本还没有Mode参数。原有Port与数据Profile参数应继续有效；例如可与 `-Profile demo` 同时使用。数据Profile的demo/schema-only与日志运行模式是两个独立维度，不得因切换debug而导入新演示、迁移业务模式或换数据库。

直接启动JAR也提供等价且唯一清楚的模式属性/环境变量，建议 `campushub.run-mode` / `CAMPUSHUB_RUN_MODE`，接受debug/release并规范大小写；未指定默认release，非法值明确失败，不静默开启debug。

## 3 配置一致性

- 最终有效模式只有一个来源规则。启动脚本显式给出的Mode优先于本机配置；没有显式参数时读取既有本机配置/环境及默认release。脚本必须在既有配置加载后应用显式参数，退出和失败时恢复它修改的进程环境，不能把调试开关遗留给下一次启动。
- 旧 `CAMPUSHUB_LOG_DIAGNOSTICS=true` 不能在明确release模式下悄悄打开诊断。给出清楚的兼容或废弃说明，让模式决定有效调试状态；避免要求用户同时改几个互相覆盖的开关。
- debug要求诊断输出实际可用；文件日志被禁用、目录不可写或其他矛盾配置需要明确处理或拒绝，不能启动后显示debug已开启却没有可用日志。沿用原日志目录检查、锁与故障保护。
- 启动安全摘要显示有效mode、诊断有效状态、版本/提交或unknown、环境和日志开关，不输出配置全集或秘密。release与debug的识别不能只靠文件名或说明文字。
- 切回release重启后，历史诊断文件保留，文件不再新增调试内容；正常运行日志和审计仍追加。不能为证明关闭而删除历史文件。
- 两种模式业务权限、校验、事务和错误码一致。debug是日志排障方式，不是绕过认证或返回隐藏数据的方式；JVM远程调试按独立配置处理。

## 4 已有模块覆盖

建立并交付一张实际接口到日志动作、模块、阶段及证据的覆盖表，不仅完善第五阶段新评论代码。先枚举已实现路由再逐项对照，不能把所有旧接口概括为AUTH或OWN_ARTICLES就算完成。

| 模块 | 应能分辨的操作 | 重点排障信息 |
| --- | --- | --- |
| 工程启动与健康 | 配置检查、应用就绪、数据库/迁移或日志目录失败、健康检查 | 有效模式和版本；安全启动失败分类；不能打印连接串和授权配置。 |
| 文章读取与分类 | 分类、列表检索、详情、图片读取 | 动作与结果、耗时；有效目标存在后可记内部ID，不记录原始关键词或任意URL。 |
| 账号与校园邮箱 | 申请注册/重置验证码、注册、登录、退出、密码重置、本人身份 | 认证/授权/校验、发送或持久化失败、频率限制及固定错误码；不记录邮箱、密码、验证码和令牌。 |
| 作者基础资料 | 本人读取、更新、独立修订冲突 | 期望/实际修订、更新阶段、事务审计；不记录昵称、简介原值。 |
| 草稿与图文创作 | 创建、本人列表、读取、保存、上传、发布、下架、恢复、删除 | 明确动作、校验/目标/回执/附件/存储/持久化/审计阶段；内部文章ID与修订；不记录正文、图片字节或资料链接。 |
| 作者主页与联系 | 文章作者入口、主页、作者文章、本人联系读取/更新、读者查看联系 | 访问者与目标权限边界、联系状态或修订、目标不可用及失败阶段；不记录联系值和个人资料。 |
| 评论与回复 | 列表、平铺回复、创建、本人删除、图片上传/读取 | 保留已实现的细分动作、根/评论/文章已验证内部ID、幂等和状态、图片权限与审计阶段。 |

主路径和可预期失败都能从HTTP响应traceId找到对应安全事件；错误码来自代码定义或严格校验，不使用用户消息做字段。ThreadLocal/MDC在请求结束、异常及线程复用时正确清理，不能把上一用户的traceId或对象ID带到下一请求。

只记录数据库已确认的内部对象标识和经过类型校验的修订，不把未经授权的请求目标当成“已存在用户/文章”。可以为状态操作保存有限白名单的状态和去重结果；读取不要求每次写数据库审计。

## 5 调试信息与日志质量

debug增加有用的阶段事件、错误分类、有限原因链及本项目类/方法/文件基名/行号。对原模块的失败同样生效，不局限于评论。5xx应能定位代码；400/401/403/404/409/429等可预期结果优先通过动作、阶段、错误码和修订排查，不生成无意义的大量堆栈。

沿用已实现的受控诊断策略，可保存校验后的SQLState和数值厂商码；不输出原始Throwable消息、SQL语句/参数、HTTP头/正文、完整用户对象、绝对配置路径或外部邮件原文。即使debug也不打印密码、验证码、令牌、邮箱、联系值、正文、图片内容与SMTP授权码。嵌套异常和第三方日志同样受此约束。

区分事务内尝试、提交成功、无变化重试和回滚。关键成功事件在提交后写运行日志，业务审计与业务变更仍同事务；日志不能出现“数据库回滚但业务成功”的叙述。调试事件不改变业务行为，不对整包或第三方依赖全局开DEBUG/TRACE。

继续保留运行/诊断分文件、容量上限、轮转、追加、目录独占及输出故障可见性；新事件真实进入文件白名单，不能只在控制台出现。避免相同异常在多层重复打印；每个请求有可关联的完成摘要。文件日志故障与数据库审计失败仍按原不同边界处理。
